## Actual authentication path on this R3 source

1. `frontend/profile.js` sets the sign-in link to `API_BASE_URL + /api/auth/github`. This is a top-level navigation to the API, not a credentialed fetch to GitHub.
2. Backend `server.js` mounts `r2.js` at `/api`. Authentication routes first wait for schema readiness. `/auth/github` requires client ID and callback URL, creates a random state in a process-local Map, and sets `r2_oauth_state` (`HttpOnly; Secure; SameSite=Lax`, path `/api/auth`, ten minutes). The GitHub authorize URL requests `read:user` and the configured callback URL.
3. `/auth/github/callback` consumes the state, requires it to be unexpired and equal to the initiating browser's state cookie, and requires an authorization code. Missing/mismatched/expired state returns 400. State is process-local: a restart or different backend instance could invalidate it; that needs deployment/log evidence and is not a confirmed cause.
4. The backend exchanges the code server-side with GitHub, fetches the GitHub identity, upserts `r2_accounts` by GitHub ID (preserving the existing account UUID and verified affiliation), and sets `r2_session`. Missing token or identity returns 401; exceptions return 500 and log `GitHub sign-in failed:`. A missing/unstable session secret is a configuration hypothesis to check privately.
5. `r2_session` is HMAC signed, expires after eight hours, and is a host-only cookie with `HttpOnly; Secure; SameSite=None; Path=/`. The callback redirects to the configured frontend's `/profile.html`. The local fix adds `?auth=github` solely to distinguish a returned OAuth attempt in error reporting. It carries no credential and grants no access.
6. The profile page fetches `GET /api/auth/me` with `credentials: include`. The backend checks the HMAC/expiry and looks up the account. Missing/invalid cookie or missing account yields 401. A valid session returns GitHub login and verification state. Credentialed CORS must allow the exact frontend origin. These separate Render hostnames require cross-site cookie behavior; `SameSite=None` does not prove a browser will store/send the cookie. Browser blocking remains a hypothesis.
7. An authenticated account with `verified: false` sees the Algoma verification form. The request endpoint requires session, exact allowed origin, configured Algoma domain, configured email transport and persistent rate limits. Code verification enforces expiry, attempt limits and atomic one-time consumption before setting `verified_at`. Private profile routes require verified affiliation. R3 separately resolves the same session UUID and requires `r2_accounts.verified_at IS NOT NULL`. No verification bypass was added.

Configuration questions: `server.js` has a default frontend origin for CORS/R3, while R2's mutation guard and callback redirect read `FRONTEND_ORIGIN` directly. An absent or malformed value can therefore cause inconsistent behavior. Confirm the actual value before changing it. Expected frontend origin is `https://cosc3506-team04-frontend.onrender.com` (no path/trailing slash); expected callback is `https://cosc3506-team-04-ey5d.onrender.com/api/auth/github/callback`, matching the GitHub OAuth app.
